## 2. 개발 루프

1. **현황 확인:** 현재 폴더, 적용되는 AGENTS, Git 변경, Unity 버전, Editor 연결 상태를 확인한다. 시작 전부터 있던 변경을 이번 작업과 구분한다.
2. **계약 연결:** 구현할 항목을 기획과 아래 검증 ID에 연결한다. 동작이 미정이면 설계 제안과 확정 규칙을 구분한다.
3. **작은 단위 구현:** 해당 책임 안에서 수정한다. 모델·View·에셋의 소유 경계를 지키고 기존 변경을 덮어쓰지 않는다.
4. **관련 검증:** 변경한 동작의 규칙 테스트와 필요한 실제 플레이 검증을 수행한다. 문서·단순 표시 변경에 구현을 복제하는 테스트를 추가하지 않는다.
5. **증거 판독:** 이번 소스·실행에 속한 결과를 확인한다. 테스트 완료 이벤트, XML, 오류와 런타임 상태를 구분해 판독한다.
6. **로컬 커밋:** 필요한 검증이 끝난 작업 파일만 확인해 커밋한다. 사용자의 기존 변경, 캐시, 비밀정보를 함께 넣지 않는다. 푸시는 별도 지시 범위다.
7. **보고:** 일반 완료 보고는 `작업 완료.`로 짧게 한다. 미검증·차단·선택 필요 시 그 이유를 정확히 알린다.

사용자가 상세 내용·원인·해결 방법·로그를 요청할 때만 프로젝트의 `log.md`를 생성하거나 갱신한다. 검증 도구가 출력하는 원시 결과 파일은 별도 증거 경로에 두며 장문의 사용자 보고로 자동 전환하지 않는다.

## 3. Unity 연결과 도구 구성

2026-09-17 사용자 요청에 따라 [Unity 공식 Codex 플러그인](https://docs.unity.com/en-us/ai/unity-plugin/codex)으로 전환했다. 공식 지원 조건은 Unity 6 이상이며 이 프로젝트의 `6000.4.6f1`을 유지한다. Codex 플러그인 `unity@unity-agent-plugin` `0.1.6-beta`(31개 스킬), 공식 Unity CLI `1.0.0-beta.10`, 이미 설치되어 있던 `com.unity.pipeline` `0.7.0-exp.1`을 사용한다. Test Framework `1.6.0`과 URP `17.4.0`도 유지한다.

Codex의 `unity` 연결은 `C:/Users/ace21/AppData/Local/Unity/bin/unity.exe mcp --project-path C:/Users/ace21/Desktop/SsalMuk`를 stdio로 실행한다. 실행 파일·프로젝트 절대 경로를 지정하며 다른 MCP 설정은 보존한다. `tools/validation/start-unity-server.ps1`도 같은 stdio 진입점이고 HTTP 서버를 따로 상주시킬 필요가 없다. `connect-unity.ps1`은 공식 CLI의 `editor_status`와 `eval`로 실제 프로젝트 경로·버전·컴파일 상태를 검사하고 `Logs/Validation/unity-connection.json`에 새 증거를 남긴다. CLI가 다른 위치에 설치되면 두 스크립트의 `-UnityCli`로 지정한다.

Codex 플러그인은 공식 저장소 `Unity-Technologies/unity-agent-plugin`을 marketplace로 등록해 설치한다. 공식 CLI 설치기는 `https://public-cdn.cloud.unity3d.com/hub/prod/cli/install.ps1`이며 설치 결과의 SHA256을 검증한다. 다른 PC에서 복구할 때는 공식 설치 문서의 현재 지원 버전을 먼저 확인하고 `unity pipeline install --project-path <프로젝트>`로 Pipeline 설치 여부를 확인한다. Codex의 새 세션에서 설치된 스킬과 `unity` MCP 도구를 불러온다. 현재 세션에서 새 도구가 아직 보이지 않아도 CLI 절대 경로로 같은 Editor에 연결할 수 있다.

모든 CLI `command` 호출에는 `--project-path <프로젝트> --caller plugin --skill unity-cli`를 붙인다(다른 공식 스킬 작업은 해당 스킬 이름). JSON 명령 목록은 파일로 받아 필요한 이름만 선택하며 전체 목록을 그대로 출력하지 않는다. Editor 작업 전 `set_autotick --enable true`로 비활성 창에서도 갱신되게 하고, 코드 변경 후 `recompile` → `recompile_status`로 완료·실패를 확인한다. 모달 창의 `blocked_by_dialog`를 게임 오류로 오인하지 않는다. 깊은 Pipeline 사용법은 `Library/PackageCache/com.unity.pipeline@*/.claude/skills/unity-pipeline/SKILL.md`를 읽는다. 패키지는 Unity Package Manager 경로로 변경하고 기존 파일 기반 검증 도구는 그대로 사용한다.

이전 A1의 Coplay 패키지·서버 `10.2.0`, Codex `unityMCP`, 8080 연결과 전용 Editor 연결 브리지는 폐기했다. 당시 `Logs/Validation/mcp-project-evidence.json`은 과거 증거로만 보존하며 재설치 지침으로 사용하지 않는다. 이번 교체의 설치·프로토콜·프로젝트 읽기·컴파일 증거는 `Logs/Validation/unity-plugin-migration-1789645736476/`에 둔다. 비밀값은 출력하거나 저장소에 복사하지 않는다.

연결 준비 완료는 **대상 프로젝트 경로·Editor 버전·읽기 요청 성공**을 함께 확인한 경우다. 다음으로 컴파일 상태와 테스트 실행 기능을 확인한다. 다른 Unity 프로젝트가 연결되었거나 도구 목록만 보이는 상태를 성공으로 보지 않는다.

| 수단 | 용도 | 경계 |
| --- | --- | --- |
| Unity 공식 플러그인·CLI·Pipeline MCP | 대상 Editor 확인, 에셋·씬 조작, 콘솔, 테스트·플레이 연결 | 프로젝트 경로 고정, 연결 실패와 게임 실패 분리, 실제 제공 명령 확인 |
| 프로젝트 파일 편집 | C#·문서·설정의 검토 가능한 변경 | 직렬화 에셋의 GUID·참조 관계 보존 |
| Unity Test Framework | EditMode·PlayMode 테스트 | 결과 파일과 종료 상태를 모두 확인 |
| Editor 테스트 API | 열린 프로젝트에서 자동 검증 | 같은 프로젝트에 두 번째 Editor를 병렬 실행하지 않음 |
| Unity 배치 실행 | Editor가 프로젝트를 점유하지 않을 때 테스트·빌드 | 정확한 설치 버전과 프로젝트 경로로 실행 |
| Git | 변경 확인, 작업 단위 커밋 | 사용자 변경 보존, 자동 푸시 없음 |

패키지·씬·프리팹 변경은 가능하면 Unity의 에셋 처리 경로를 사용하고, 변경된 에셋과 `.meta`의 연결을 확인한다. 수동으로 직렬화 파일을 수정했다면 import 후 참조와 실제 로드를 확인한다. 사용자 작업 때문에 Editor 재시작이 필요한 경우 현재 열린 씬과 미저장 상태를 먼저 확인한다.

## 4. 검증 도구의 구조

PowerShell 7.5 이상의 `tools/validation/validate.ps1`을 공통 진입점으로 구현했다. `Static`, `EditMode`, `PlayMode`, `Smoke`, `Stress` 모드를 명시적으로 선택하고, 모든 변경에 가장 무거운 모드를 자동 실행하지 않는다. Smoke는 EndToEnd·RepeatedRestart, Stress는 CrowdCorridor·PersistentWorld10m·PersistentWorld30m·HighGrowth를 지원한다. 알 수 없는 이름과 모드 조합을 거절한다. 시나리오도 실행 ID·소스 해시·시각·필수 관측·실제 주기 수·성능 필드와 결과 파일 해시를 모두 대조한다.

Windows 개발 빌드는 열린 Editor의 `BuildValidator.QueueWindows`로 MainMenu·Battle을 명시해 생성한다. Unity가 빌드 중 자동 저장하는 설정은 실행 전 파일을 백업하고 성공/실패 모두 복원한다. `tools/validation/run-build-smoke.ps1`은 해당 빌드의 실제 exe로 위 여섯 시나리오를 실행하고 소스 일치·종료 코드·결과를 확인한다. 숨긴 창의 촬영은 같은 런타임 카메라와 활성 UI를 별도 렌더 대상으로 그린 결과이며, 해당 관측을 기록한다. 측정 조건과 실제 통과 실행은 [D3 검증](D3_VALIDATION.md)을 따른다.

현재 입력은 프로젝트 경로, 검증 모드, 이름 필터, 시나리오 이름, 제한 시간, 닫힌 프로젝트용 Unity 경로다. 각 시나리오의 시드·설정 프리셋은 ScenarioDefinition과 실행 결과에 명시한다. 결과 경로는 실행기가 새로 정한다. 실행기는 동일 프로젝트 점유 상태를 검사하며, 유효하지 않은 경로·컴파일 실패·테스트 시간 초과·빈 검색 결과를 실패로 남긴다.

제한 시간은 기본 180초다. 오래 걸리는 진단은 Editor 진입점에 최대 14,400초, Windows 실행 파일 진입점에 최대 43,200초를 명시할 수 있다. 요청에 기록된 기한을 넘기면 취소한다. 이는 검증 도구의 기한이며 게임의 생존 시간이나 개체 수를 제한하지 않는다. Windows 실행의 manifest에는 해당 프로세스 ID도 기록한다. 같은 실행 ID의 `cancel.json`이 있거나 실행 도구가 오류로 종료되면 직접 시작한 프로세스를 정리한다.

결과 경로는 기존 Unity 무시 규칙에 포함되는 `Logs/Validation/<새 실행 ID>/`다.

| 출력 | 내용 |
| --- | --- |
| `manifest.json` | 실행 ID, 시작·종료 시간, 프로젝트 경로, Unity·패키지 버전, Git HEAD와 관련 소스 해시, 시드·프리셋·모드·필터 |
| `editmode.xml`, `playmode.xml` | 해당 모드를 실제 실행했을 때 생성된 테스트 결과 |
| `receipt.json` | 실행 ID·소스 해시·시간·버전, 발견한 테스트 전체 이름, XML 해시, 완료/실패 원인 |
| `scenario.json` | 수행한 시나리오, 필수 관측, 실제 주기 수, 실패 지점, 시간·메모리 측정과 개체·대기량 표본 |
| `progress.json` | 장시간 시나리오의 최근 시뮬레이션 시간·개체 수·처리 주기 수 |
| `build.json`, `standalone-manifest.json` | Windows 개발 빌드와 실제 실행 파일 검증, 소스·실행 파일·설정 보존 해시 |
| 화면 증거 | 필요한 경우 해당 실행에서 얻은 화면 또는 영상 |
| Editor 원시 출력 | 컴파일·런타임 예외와 도구 오류의 근거 |

통과 판독기는 결과의 실행 ID·시간·소스 상태가 이번 실행과 일치하는지 확인한다. 예상 테스트가 실제 발견·실행되었는지, 실패·오류가 없는지, 필수 항목이 건너뛰어지지 않았는지를 확인한다. **종료 코드 0, 예전 XML, 테스트 0개, 화면 한 장만으로 통과하지 않는다.** 실행 뒤 관련 소스가 바뀌면 그 결과는 수정 후 검증으로 재사용하지 않는다.

PowerShell 7에서 다음 명령을 사용한다.

```powershell
./tools/validation/validate.ps1 -Mode Static
./tools/validation/validate.ps1 -Mode EditMode -Filter SsalMuk.Tests.ValidationBridgeTests
./tools/validation/validate.ps1 -Mode PlayMode -Filter SsalMuk.Tests.ValidationPlayModeTests
```

필터는 정규식이 아닌 이름 접두사다. 테스트는 해당 모드의 `SsalMuk.Tests.*` 조립 단위 안에서 검색한다. 미저장 씬이 있으면 `EditorBusy`로 실패하며 강제로 저장하지 않는다. 활성 요청은 SessionState로 유지하고 PlayMode 종료·씬/설정 복원 후 소스 상태를 대조한다. Windows의 잠깐 파일 잠금은 제한된 재시도로 처리하고, 지속되는 오류를 통과로 바꾸지 않는다.

A~D에서 모델·Unity 표시·통합 시나리오·Windows 실행을 확인했다. D3 게임 코드의 EditMode 175개·PlayMode 21개·짧은 시나리오 4종·10분 누적·Windows 시작/전투/사망/재시작이 통과했다. 30분은 기한 초과로 미완료다. 이후 Windows 검사 도구 확장에 대한 검증 범위와 설정 캐시 문제는 [D3 결과](D3_VALIDATION.md)를 따른다. 2026-09-17 사용자의 검사 종료 지시에 따라 추가 실행 없이 [실제 플레이·밸런스](PLAYTEST_TUNING.md)로 전환한다.

## 5. 재현과 관측 경계

- Core는 시간을 직접 읽지 않고 Step으로 전달받는다. 테스트에서는 5분·10분 경계까지 모델 시계를 진행해 예약 규칙을 확인한다.
- 맵·스폰·선택지 난수 스트림을 분리한다. 동일 맵 시드에서 보상을 더 많이 선택해도 지형이 달라지지 않아야 한다.
- 모델 ID, RunId, OfferId, 생성 일정 ID, 공격 ID를 관측 가능하게 한다. View나 풀의 인스턴스 ID만으로 논리 개체를 추적하지 않는다.

- 맵 시드와 조작 기록만으로 다른 Unity 버전의 화면·부동소수점 결과까지 동일하다고 주장하지 않는다. 테스트 환경과 허용 오차를 기록한다.

## 7. 성능과 무한 보존 검증

측정에는 하드웨어, 빌드/Editor 구분, 해상도, 시드, 경과 시간, 논리 몬스터·경험치 수, 표시 객체 수, 최고 강화 단계를 함께 남긴다. 렌더링 비용과 모델 계산 비용을 분리하고 CPU 프레임 시간, 메모리, 할당, 경로 요청 대기, 예약 공격 처리 지연을 본다.

2026-09-17 몸통·피격 분리 후 비교는 `validate.ps1 -Mode PlayMode -Filter SsalMuk.Tests.CrowdPerformanceComparisonTests -TimeoutSeconds 420`으로 실행한다. 외부 소스 변경 후 공식 CLI의 `recompile` 및 `recompile_status` 완료를 확인한 다음 요청한다. 300/500/1000 이동 전용 조건은 장애물 없는 간격 0.58 배치, 플레이어 입력·전투·소환·경험치 없음, 실제 개발 에셋의 정의와 FixedUpdate/WorldPresenter/UnitView를 사용한다. 별도 1000 전투 조건에는 플레이어 AI·기본 무기 4종·접촉·초기 경험치 200개를 켜고 높은 fixture 체력으로 개체 수를 유지한다. 실제 게임 상한 500은 변경하지 않는다.

예열 40 고정 주기 후 측정 350 고정 주기(게임 시간 7초)와 렌더 간격 최소 20개를 요구한다. 예열 45초·측정 90초 한도를 넘겨 표본이 부족하면 실패한다. 카메라 반높이 24·표시 반경 60을 모든 조건에 동일 적용한다. 이전 그림자 비교는 벽시계 예열 2초·렌더 간격 20개·카메라 반높이 12였으므로 참고 자료와 엄밀한 동일 조건 전후 비교를 구분한다. VSync·목표 FPS·백그라운드 설정을 종료 때 복구하고 고정 갱신 주기·최대 누적 시간은 바꾸지 않는다.

비교 JSON은 `Logs/Validation/CrowdPerformance/<runId>/report.json`에 쓰고 테스트 XML의 출력 경로와 검증 manifest·receipt를 연결한다. 모델 시간은 이동 갱신 한 번, 표시 시간은 Presenter 갱신 한 번, 프레임 시간은 연속 LateUpdate 사이 실제 벽시계 시간이다. 표시 시간은 GPU 시간이나 전체 렌더 시간과 다르다. 스레드 할당 카운터는 실제 할당 탐침으로 지원 여부를 확인하며 미지원이면 -1을 기록한다. 한 번씩 수행한 짧은 밀집 비교이며 일반 생존 플레이·장시간·빌드 FPS 보증으로 사용하지 않는다.

단계적 시나리오는 기본 생존, 여러 보스 생존, 경험치 미수집 채 방랑, 큰 강화 단계, 반복 재시작이다. 우선 10분·30분 구간과 개체 수를 올린 인위적 부하를 비교한다. 이 시간과 개체 수는 측정 구간이며 게임 종료 시간이나 스폰 상한이 아니다.

지원 성능 수치는 실제 측정 후 확정한다. 느리면 공간 검색·경로 재사용·표시 풀·효과 묶음 등 동작을 보존하는 개선을 먼저 검토한다. 경험치 삭제, 일반·보스 삭제·동결, 보스 상한, 강화 상한, 공격 발동 누락을 최적화로 몰래 넣지 않는다. 공중의 돌진 후 퇴장은 2026-09-17 사용자가 정정한 게임 규칙이며 성능을 위해 숨겨 둔 삭제가 아니다.

## 8. 작업 완료 판정과 인계

개별 작업의 완료는 해당 기획 계약, 수정한 소스·에셋, 필요한 테스트, 관련 실제 동작이 확인된 상태다. 실제 확인하지 못한 항목은 실행 성공과 구분한다. 문서 작업에는 문서의 링크·일관성·변경 범위 확인을 적용하며 게임 테스트 완료라는 표현을 쓰지 않는다.

구현 전체 완료는 H01~H30 중 적용되는 시나리오를 실제 구현으로 검증하고, 구조 설명과 측정 한계를 함께 남긴 뒤 판단한다. 타격감·AI 운영·난이도의 만족도는 플레이테스트로 조정한다. 초기 스탯만 바꾸면 모든 문제가 해결된다고 가정하지 않는다.

다음 작업에서 읽을 순서는 게임 기획서 → 구조 설계 → 하네스 → 승인된 구현 계획이다. 누락된 실행 도구나 연결 실패가 있으면 그 상태에서 이어 진행하며, 설계 문서만 보고 이미 구축·검증한 것으로 간주하지 않는다.
